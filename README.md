# LogiFlow

**Logistics operations, without the chaos.**

LogiFlow is a full-stack logistics operations management application that models a real courier/logistics business — customer intake, dispatch, driver execution, proof of delivery, payments, and public shipment tracking — across four distinct experiences: **Admin**, **Dispatcher**, **Driver**, and **Public Tracking**.

It's a portfolio project built to demonstrate the ability to build real internal business software — not just customer-facing storefronts — with database-enforced business rules, role-based authorization, and a real operational audit trail.

🔗 **Live demo:** [logiflow-orcin.vercel.app](https://logiflow-orcin.vercel.app/)
📦 **Repo:** [github.com/Vivianclare-codes/logiflow](https://github.com/Vivianclare-codes/logiflow.git)

## Why this project exists

Most portfolio projects are storefronts or to-do apps. LogiFlow is an attempt at something closer to what a company would actually hire a developer to build and maintain: a role-based operations system where the database — not just the UI — enforces who can do what.

The core question it answers: *can this developer build software with real authorization boundaries, transactional business logic, and an audit trail, not just CRUD screens?*

---

## The workflow it models

```
Customer exists
  → Shipment created
  → Pickup scheduled
  → Driver + vehicle assigned
  → Picked up
  → In transit
  → Out for delivery
  → Delivered
  → Proof of delivery recorded
```

Every shipment has a **current status** (`shipments.status`) and a **full history** (`shipment_events`) — these are deliberately separate, so both operational dashboards and the public tracking timeline can be built from real data.

---

## The four experiences

LogiFlow is one product, four different surfaces, each with its own permissions:

| Role | Access |
|---|---|
| **Admin** | Full system access — staff, customers, drivers, vehicles, shipments, payments, activity |
| **Dispatcher** | Day-to-day ops — create shipments, assign drivers/vehicles, schedule pickups, update statuses |
| **Driver** | Restricted portal — only their own assigned shipments, delivery status updates, proof of delivery |
| **Public** | No login — track any shipment at `/track/[trackingNumber]` with safe, limited fields only |

There is intentionally **no customer account system** in the MVP — customers track shipments via a public tracking page, not a portal.

## Feature highlights

- **Authentication & authorization** — Supabase Auth, role-based routing, active/inactive staff accounts
- **Staff management** — role changes are blocked when business rules require it (e.g. a driver with active shipments can't be reassigned), not just discouraged in the UI
- **Dispatch** — driver/vehicle assignment, reassignment, and unassignment, with availability enforced at the database level, not just filtered in the UI
- **Shipment workflow** — controlled status transitions via PostgreSQL functions, with a separate historical event log
- **Driver portal** — a genuinely different, restricted execution surface, not an Admin dashboard with fewer buttons
- **Public tracking** — served through `SECURITY DEFINER` RPCs that return only safe fields, never a direct table query
- **Proof of delivery** — recipient, timestamp, notes, recorded-by, tied 1:1 to a shipment
- **Payments** — manual payment recording, multiple payments per shipment, automatic balance calculation, overpayment prevention
- **Activity log** — an operational audit trail generated by triggers and RPCs, not by the UI
- **Live dashboard & landing page metrics** — real database queries, no hardcoded numbers anywhere

## Tech stack

**Frontend:** Next.js (App Router), TypeScript, React, Tailwind CSS, shadcn/ui
**Backend:** Supabase (PostgreSQL, Auth, Storage, Row-Level Security)
**Forms/validation:** React Hook Form + Zod
**Deployment:** Vercel + GitHub

No separate Node/Express backend — reads happen through Server Components, writes go through Server Actions and PostgreSQL RPCs where a transaction or business rule needs to be enforced atomically.

```
Browser
  → Next.js
      ├─ Server Components   (reads)
      ├─ Server Actions      (writes/orchestration)
      ├─ Proxy/middleware    (route protection, UX)
      └─ Client Components   (forms, dialogs, interactivity)
  → Supabase
      ├─ PostgreSQL
      ├─ Auth
      ├─ Row-Level Security
      └─ Storage
```

## Security model

The core principle: **RLS is the real security boundary — not the UI, and not middleware.**

- Route protection/middleware exists for UX, not as the authorization layer
- Every one of the 10 application tables has Row-Level Security enabled
- Drivers can only read/write their own assigned shipments — enforced in the database, not just hidden in the UI
- Public tracking never queries `shipments` directly; it goes through `SECURITY DEFINER` functions that return a narrow, safe field set
- Resource availability (driver/vehicle busy status) is checked in PostgreSQL functions, not just filtered client-side — a malformed or malicious request still can't double-book a driver

This was tested directly: a driver attempting to open another driver's shipment URL gets a 404, not a hidden-but-reachable page.

---

## Database

10 application tables: `profiles`, `customers`, `drivers`, `vehicles`, `shipments`, `shipment_events`, `proof_of_delivery`, `payments`, `activity_logs`, plus Supabase's `auth.users`.

Key relationships:
- Shipments cascade to their events, POD, and payments
- Customers and drivers are protected from deletion where shipment history depends on them
- Tracking numbers (`LG-0001`, `LG-0002`, ...) are generated by PostgreSQL, never assigned by the application

Business logic that matters is enforced in PostgreSQL functions, including `assign_shipment_resources()`, `update_shipment_assignment()`, `unassign_shipment_resources()`, `complete_shipment_delivery()`, `record_shipment_payment()`, and the public-safe `get_public_shipment()` / `get_public_shipment_events()` / `get_public_dashboard_stats()`.

## What building this taught me

- Authentication and authorization are different problems, and middleware isn't the second one
- UI restrictions are a convenience, not a security boundary — the database has to enforce the real rules
- "Current state" and "history" are different data concerns, even when they describe the same object
- Seed/demo data inserted directly can bypass the same business rules the app is supposed to enforce — which is exactly how you find out if your rules are real
- A demo environment is still a real, mutable application state, and treating it otherwise is how portfolio demos quietly break
